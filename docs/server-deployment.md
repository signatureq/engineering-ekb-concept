# СК Орион: статьи и серверная админка

## Что работает сейчас

GitHub Pages публикует только готовый публичный сайт. Раздел `/articles.html` и шесть статей работают без сервера. Админка Django находится в исходниках `server/`, но в артефакт Pages не попадает. Публичная `/admin/` на GitHub Pages не работает — это ожидаемо.

На сервере `/admin/` позволяет создавать статьи, сохранять черновики, смотреть закрытый предпросмотр, загружать фотографии, публиковать и снимать материалы с сайта. В основной форме — название, текст и фотография. Служебный адрес страницы, краткое описание и технические поля создаются автоматически. В свёрнутом блоке «Дополнительно — вид в поиске» можно задать название и описание для поиска; пустые значения сайт заменит названием и выдержкой из текста. Отдельно можно менять название компании в шапке и подвале, телефон и вводный текст главной. Услуги и портфолио пока редактируются в исходниках. Заявки отправляются серверным обработчиком через FormSubmit после подтверждения почты получателя.

Сохранение черновика не меняет публичную статью. Кнопка «Опубликовать» собирает отдельную полную версию сайта и переключает её целиком. При ошибке сборки предыдущая версия остаётся на месте. Адрес статьи после первой публикации закрепляется. «Снять с публикации» убирает страницу, оставляя её в редакторе. Опубликованный материал нельзя удалить, пока он не снят с публикации.

Визуальный редактор работает как обычный документ: абзацы, подзаголовки, списки и выделения добавляются кнопками. Клиент не вводит Markdown или HTML. Внутри текст сохраняется в безопасном Markdown; произвольный HTML отключён. Редактор Quill 2.0.3 и конвертер Turndown 7.2.1 поставляются локально с лицензиями, без зависимости от внешнего CDN. Обложки JPG/PNG/WebP до 5 МБ и 16 Мп преобразуются в WebP, уменьшаются до 1800 px и сохраняются без EXIF. Черновые фотографии доступны только вошедшему редактору; при публикации появляется публичная копия.

## Локальный запуск

Нужен Python 3.12 или новее. Выполнять из корня репозитория:

```sh
python3 -m venv .venv
.venv/bin/pip install -r server/requirements.txt
export DJANGO_DEBUG=1
.venv/bin/python server/manage.py migrate
.venv/bin/python server/manage.py seed_content
.venv/bin/python server/manage.py createsuperuser
.venv/bin/python server/manage.py runserver 127.0.0.1:8766
```

Сайт: `http://127.0.0.1:8766/`, вход: `http://127.0.0.1:8766/admin/`. Данные хранятся в игнорируемом `.local/cms-data/`. У production нет стандартного логина или пароля: владельца создают отдельно. Локальный тестовый аккаунт не переносится на сервер.

## Рабочий сервер

18 октября 2026 сайт развёрнут на Ubuntu 24.04, `176.12.67.40`, в `/opt/orion/site`. Docker Compose запускает CMS, внутренний Nginx и внешний Caddy. Проверены реальная сборка образа, HTTPS, вход редактора, сохранение, предпросмотр, публикация и снятие статьи с публикации. Временный проверочный материал удалён. Существующие GitHub Pages и `stroy-ekb.ru` продолжают работать отдельно.

Временный защищённый адрес — `https://176.12.67.40/`, вход — `/admin/`. Для IP выпущен доверенный сертификат Let's Encrypt; Caddy автоматически продлевает короткоживущие сертификаты. `default_sni` нужен клиентам, которые не передают SNI при обращении по IP. IP-версия возвращает `X-Robots-Tag: noindex,nofollow`.

Новый основной домен — `инженерные-работы96.рф` (`xn---96-6cdfvaagt9ccbsyd1b9kh.xn--p1ai`). В последней проверке DNS возвращал NXDOMAIN. На сервере уже подготовлены оба имени и canonical/sitemap; сертификат домена появится после делегирования DNS и записей `@ A 176.12.67.40`, `www CNAME xn---96-6cdfvaagt9ccbsyd1b9kh.xn--p1ai.`. Изменять `CNAME` GitHub Pages при этом не требуется.

Клиентский аккаунт `orion` входит в группу «Редакторы» и не имеет прав суперпользователя. Случайный пароль передаётся отдельно в приватном файле; в исходниках его нет. Локальные тестовые пользователи не переносились. Реальный `.env` — `/opt/orion/site/server/.env`, права `600`.

## Запуск на VPS с Docker Compose

Нужен VPS с Docker Compose, а не тариф только со статическими файлами. Следующие команды выполняются из корня репозитория; на рабочем сервере использовать проект `-p orion` и оба compose-файла, как в примере.

1. Скопировать репозиторий на сервер. Создать `server/.env` по `server/.env.example`, права `600`. Вставить уникальный `DJANGO_SECRET_KEY` (например, результат `python3 -c 'import secrets; print(secrets.token_urlsafe(64))'`). Оставить `DJANGO_DEBUG=0`. Проверить домены и доверенные HTTPS origins. Реальный `.env` не коммитить.
2. Из корня выполнить:

```sh
docker compose -p orion -f server/compose.yaml -f server/compose.edge.yaml up -d --build
docker compose -p orion -f server/compose.yaml -f server/compose.edge.yaml exec cms python server/manage.py createsuperuser
docker compose -p orion -f server/compose.yaml -f server/compose.edge.yaml logs --tail=100 cms
```

3. В `server/.env` заполнить `SITE_ADDRESS` (домены через запятую), `SERVER_IP` и `PUBLIC_SITE_URL` (основной HTTPS origin без пути). Домены и origins должны совпадать с `DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS`; для кириллицы использовать punycode. `PUBLIC_SITE_NOINDEX=1` и `SITE_ROBOTS_POLICY=noindex,nofollow` подходят для закрытого от индексации тестового экземпляра. Для основного сайта — `0` и `all`. Изменение env требует пересоздания CMS и Caddy.

Внешний HTTPS-прокси уже входит в `compose.edge.yaml` и `server/Caddyfile`. Внутренний Nginx привязан только к loopback порту 8080. Не открывать его напрямую в интернет: конфигурация предполагает, что перед ним работает HTTPS. Порты 80/443 должны быть доступны, а DNS домена — указывать на IP VPS. Текущий GitHub Pages до переключения продолжает работать.

4. Проверить HTTPS, вход, сохранение черновика, предпросмотр и публикацию тестовой статьи. Для заявок отдельно заполнить почту FormSubmit, как описано ниже. Затем создать редактора через раздел пользователей: отметить «Статус персонала», добавить в группу «Редакторы», не выдавая статус суперпользователя.

Команда старта выполняет миграции, импорт начальных материалов и сборку статики. Повторный `seed_content` не перезаписывает существующие статьи, в том числе черновики изменений, и настройки. Данные лежат в постоянном томе `cms-data`. Не использовать `docker compose down -v`: это удалит базу и фотографии.

## Резервное копирование и восстановление

На рабочем сервере установлен `orion-backup.timer`: каждый день около 03:20 UTC он запускает `server/backup.sh`. Копии базы, фотографий и production env находятся в `/var/backups/orion/`, доступны только root и хранятся около 14 дней. Первая копия создана и проверена. Это копии на том же VPS: для защиты от потери сервера их нужно дополнительно выгружать во внешнее защищённое хранилище.

Установка таймера на новом сервере:

```sh
install -m 750 server/backup.sh /usr/local/sbin/orion-backup
install -m 644 server/orion-backup.service server/orion-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now orion-backup.timer
systemctl start orion-backup.service
systemctl list-timers orion-backup.timer
```

Для ручного копирования можно использовать отдельную команду:

```sh
docker compose -p orion -f server/compose.yaml exec cms python server/manage.py backup_cms --output /data/backups/2026-10-18
docker compose -p orion -f server/compose.yaml cp cms:/data/backups/2026-10-18 ./private-backup-2026-10-18
```

Каждый раз нужен новый каталог. В нём согласованная SQLite-копия с пользователями, черновиками и опубликованными версиями, а также оригиналы загруженных изображений. Это приватные данные: хранить их вне публичного сайта. Сам `.env` сохранять отдельно в защищённом месте. Старые резервные копии удалять по принятому сроку хранения.

Для восстановления остановить CMS, вернуть `cms.sqlite3` и каталог `media/` из одной копии в `/data`, восстановить владельца UID 1000 и права базы `600`, затем запустить CMS. Старт пересоберёт публичный сайт из опубликованных снимков. До переключения домена проверить вход и фотографии. Если восстановление идёт в отдельный экземпляр, отключить старый, чтобы редакторы не публиковали одновременно в две разные базы.

## Обновление и проверки

Перед обновлением сделать копию. Обновить исходники и выполнить `docker compose -p orion -f server/compose.yaml -f server/compose.edge.yaml up -d --build --force-recreate`. Это сохраняет данные тома и обновляет файловые bind-mount после распаковки исходников из архива. Поддерживать Django/Pillow/Gunicorn в актуальной исправленной версии. Проверки приложения:

```sh
DJANGO_DEBUG=1 .venv/bin/python server/manage.py test tests
DJANGO_DEBUG=1 .venv/bin/python server/manage.py check
.venv/bin/python scripts/build_site.py --output-dir .build/public
```

Для production дополнительно выполнить `manage.py check --deploy` с production env и проверить HTTPS через внешний прокси. Часовой пояс публикаций — Екатеринбург.

## Как хранится содержимое

- Начальные статьи: `content/articles.json` и Markdown в `content/articles/`.
- Генератор: `scripts/build_site.py`; `--output-dir` создаёт только публичные страницы и ресурсы. В репозиторий не добавлять базу CMS и `.env`.
- После переноса редакторские правки живут в SQLite и media на сервере. GitHub Pages не синхронизируется с этой базой автоматически. Основной сайт после переключения DNS обслуживает VPS.
- При необходимости выгрузить опубликованные тексты: `manage.py export_content --output /private/new-export`. Вместе с JSON скопировать `/data/public/assets/uploads/` для обложек; не копировать приватные данные целиком в веб-корень.
- На GitHub настроен workflow Pages: в него попадает `.build/public`, а не весь репозиторий. Админка, исходные Markdown, черновики, пользователи и пароли не входят в публичный артефакт.

## Заявки через FormSubmit

Серверный `/api/inquiry/` выдаёт CSRF-токен и признак доступности при GET, принимает форму при POST. `INQUIRY_TO_EMAIL` задаётся в `server/.env`; пустое значение выключает отправку. После изменения выполнить `docker compose -p orion -f server/compose.yaml -f server/compose.edge.yaml up -d cms`. API-ключ и домен отправителя не требуются. Получатель на рабочем сервере — указанная владельцем почта Яндекса. `PUBLIC_SITE_URL` используется как постоянный Origin/Referer исходящих запросов при обращениях с домена или временного IP.

При первом запросе FormSubmit отправляет получателю письмо с кнопкой «Activate Form». Её должен нажать владелец ящика. Ответ `success: "false"` с запросом активации возвращает 503, а не успех. После активации сделать настоящую тестовую заявку и подтвердить получение письма с вложением. Доступность HTTPS сама по себе не подтверждает доставку.

Получатель не принимается из формы. Успех требует явного `success: true` или `"true"` в JSON-ответе FormSubmit. Таймаут и отклонение возвращают ошибку, сохраняющую заполненную форму. Случайный номер заявки помогает различать письма; FormSubmit не предоставляет используемого здесь ключа идемпотентности, поэтому повтор после неясного сетевого сбоя может дать дубликат. Заявки не сохраняются в базе CMS: письма поступают в выбранный почтовый ящик.

Вложений — до пяти, общим размером до 10 МБ; допустимы только форматы, указанные у формы. В FormSubmit они передаются как multipart-вложения, не сохраняются в публичном каталоге. Проверяются поля, длины, служебное поле для ботов и CSRF; Nginx ограничивает частоту обращений по реальному IP. GitHub Pages не содержит серверного API: только на `stroy-ekb.ru`, `www.stroy-ekb.ru` и `signatureq.github.io` при его 404 форма отправляет multipart напрямую в FormSubmit. На сервере используется свой API. Адрес получателя для этой статической копии задан в `script.js`; при смене почты обновить его вместе с серверным env. Оба пути проверяют явное подтверждение успеха от сервиса.

Проверка без реальных писем: `DJANGO_DEBUG=1 .venv/bin/python server/manage.py test tests.test_inquiries`. Тесты проверяют получателя, двоичные вложения, CSRF, валидацию, отсутствие конфигурации, активацию, строковый отрицательный ответ, отклонение и таймаут провайдера.
